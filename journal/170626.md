**Daily Project Journal: Seal Online Web Portfolio Data Retrieval**

**Date:** 17 June 2026

Today, I continued refining the monster data retrieval pipeline for the Seal Online web portfolio project. The main focus was on improving the database structure, strengthening the parser logic, and cleaning up exported development artifacts so that the import process is more reliable before a full rerun.

One of the major tasks was restructuring the database schema into a more normalized design. Instead of storing all drops in a single generalized item model, I separated the data into dedicated tables for maps, items, gems, pets, weapons, armors, accessories, and battle pet equipment. I also defined the join tables `monster_locations` and `monster_drops` so that monster relationships can be stored explicitly. After that, I updated the repository layer so the importer now writes parsed entities into the correct tables and links them through the new relationships. This makes the schema easier to extend later and avoids the earlier duplication problems.

Another important part of today’s work was debugging the monster parser. I fixed the level parsing issue where values such as `9 / 21` were incorrectly interpreted as unrelated numbers from the same table. The parser now extracts all numeric values from the level field and stores the lowest level. I also improved the pet-drop parsing logic. Previously, broken wiki markup could cause incorrect pet entries such as `File:Piya egg.gif` or even the monster name itself to be saved as a pet. I introduced a stricter pet extraction flow that ignores file-description anchors, uses nearby media blocks more carefully, normalizes fallback names such as `Piya Egg`, and builds a usable wiki URL even when the HTML only exposes a broken upload link.

In addition, I reviewed database indexing for performance. A Supabase warning highlighted that `monster_drops` needed clearer foreign-key indexing, so I added explicit indexes for each nullable relationship column, including `item_id`, `gem_id`, `pet_id`, `weapon_id`, `armor_id`, `accessory_id`, and `battle_pet_equipment_id`. This should make relationship queries more efficient and reduce advisor warnings when the schema is recreated.

I also cleaned up generated JSON artifacts used during parser debugging. The project no longer keeps the per-monster JSON export folder for the `16-30` page, while the page-level JSON snapshot remains available for inspection. This keeps the development workspace cleaner while preserving the main parsed output needed for testing.

Overall, today’s progress moved the project closer to a stable import workflow. The next step is to rebuild the database using the updated schema and rerun the importer so the normalized schema and corrected parser logic can be tested together on the full monster dataset.
